I

The problem

A small studio's operation fits in a spreadsheet until it stops fitting. The proposal in one file, the invoice in another, whatever was agreed with each client living in the memory of whoever took the call, and the next step of each deal nowhere at all. The cost does not show up at once: it shows up as a forgotten invoice, a follow-up that never went out, and a client question nobody can answer without digging.

The goal was not to have a CRM. It was to have one place where sales, delivery, finance and support look at the same data, under the same rules about who can see what, and where the day's work is already assembled before anyone asks what to do next.

II

Five surfaces, one model

One Next.js application serves five very different things over the same data model and the same authorization layer. There were four in August; the content studio arrived in October without creating a new access rule of its own.

  1. 01 Web dashboard Where the operation happens: kanban funnel, daily queue, finance and metrics, with a chat on every screen that proposes typed operations and executes nothing on its own.
  2. 02 MCP server 121 tools that let an AI agent run the system by conversation. There were 70 in August.
  3. 03 Token-based public pages Commercial proposal, client portal and project status, opened by link, no login.
  4. 04 Scheduled routines Invoicing, revenue snapshots, a daily briefing and invoice issuing for a retail client, now on systemd timers.
  5. 05 Content studio Topics, pieces and posts for the Kyber and Didata profiles, with per-project roles and a worker on a desktop PC to render video. Nothing is published without a human action.

The interesting part is not how many surfaces there are, it is that all of them share the same business rules and the same per-user isolation instead of each reimplementing its own version. A rule fixed once holds for the dashboard, the agent, the public page and the scheduled job at the same time.

III

How it was solved

Per-token identity in the MCP server

All 121 tools run under one endpoint, and who is operating is resolved from the request token. Identity is propagated through AsyncLocalStorage so it cannot leak between concurrent requests. Each partner operates only their own data, under the same rules as the dashboard.

Authorization in the database, not the app

276 live RLS policies across 78 tables, with SECURITY DEFINER functions for the composite decisions: who can see which lead, who is an admin, who can reach which area. The front end is never the security boundary. Since the migration, the server derives identity from the session and connects with roles that lack bypassrls, and startup refuses to boot if any login holds that power.

Prospecting cadence engine

A sequence of three touches with distinct angles and growing intervals. There were four until September. Measured over the 1,542 touches recorded in the database, the third one, social proof, got replies at the same level as the first and was cut; the closing one stayed, because it is the one that returns the lead for recycling. Prioritisation uses signals from the lead: public rating, review volume, digital presence and historical niche. There is a daily cap per person and a global opt-out list. A reply from the lead pauses the automation and hands the case back to a human.

AI applied narrowly, with a brake

Specific uses: draft the opening approach, draft a proposal from the catalogue, write a follow-up by reading the conversation history, produce the daily read of the numbers and, since October, the operational chat and the studio's writing assistance. Each with explicit rules against inventing a price, a deadline or a deliverable, plus a review layer that re-reads the generated text and flags claims the system state does not support.

Multi-user with revenue split

Lead sharing between partners, a percentage per lead and payout calculation, with finance respecting the split. Per-user isolation and revenue split are the same problem seen from two sides.

IV

Automate everything except the last mile

The system never sends a message automatically, on any channel, and that is deliberate. It builds the queue, writes the text and records the send, but the send click is always human. There is an optional pilot of a sales agent, capped at ten conversations and gated by an admin; it is ready and has not been switched on.

The reason is operational and legal risk. The official API requires documented consent the base does not have. The unofficial alternatives violate the terms and get the account banned. And the number used for prospecting is the same one that serves the clients who already pay.

Automating the send would save minutes and put the main channel of the business at risk. The trade does not pay. The system is designed around that choice, not in spite of it.

VI

Leaving the cloud with no way back

On 31 Oct 2026 at 9:28 pm, the CRM left Vercel and Supabase and started running on its own server, with its own Postgres, authentication and file storage.

The risk in a migration like this is not the cutover day, it is the day after: if the destination takes a write and something goes wrong, pointing DNS back to the origin silently loses that write. So the origin was locked before the final capture, and the rule was written down: after the first write on the destination, recovery is always of the destination, never a return to the cloud.

The final capture was encrypted, restored in a single transaction and compared before COMMIT: 146 tables, 11 sequences and the files checked by hash. Only then did the public address change. The scheduled 9:30 pm backup, two minutes later, already captured the open destination, and it was downloaded and decrypted off the server to prove it restores.

What is not proven yet is said out loud: the goal of losing at most one hour of data and rebuilding the whole server in two hours has not been shown in a drill. It is recorded as pending, not as fact.

One note came out of this case: RLS in the database or authorisation in the application.
